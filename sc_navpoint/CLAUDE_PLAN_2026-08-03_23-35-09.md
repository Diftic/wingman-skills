## 5. Release blockers

### B1. The primary surface scenario is unsupported on non-`OOC_` bodies

`payload_from_rows` emits a local frame only when it finds an `OOC_` row. Pyro uses body rows such as `Zone: pyro3 ...` without the prefix. The current planetary-scale guard safely refuses that case rather than misclassifying it as open space.

This is correct fail-closed behavior, but it contradicts the discovery text and tool description that claim marking works on any planet or moon surface.

The user raised a new working hypothesis on 2026-08-03: `OOC_` may belong to one planetary-system convention rather than being universal. Do not encode that as fact yet. The existing `OOC_Stanton_4b_Clio` example is from Clio, a microTech moon, so the evidence does not support a Crusader-only interpretation. Plausible alternatives include a Stanton-wide convention, a planet-tech generation, or an object-container naming convention used by only some bodies. The surface survey below must determine the actual boundary.

### B2. Essential work is not recoverable from Git

At plan creation NavPoint had:

- 12 modified tracked files;
- about 725 untracked files;
- untracked runtime modules;
- an entirely untracked test suite;
- an untracked `release_version/`;
- about 327 MiB under `ocr_dev/` and 42 MiB under `screenshots/`.

The root `sc_navpoint_v4.9.0.0.zip` dates from 2026-07-18 and is not the installed 4.9.0.22 build.

### B3. The local HUD is exposed more broadly than necessary

The FastAPI server binds to `0.0.0.0` while exposing unauthenticated mutation endpoints. The static handler joins a caller-controlled path without resolving it and proving it remains under the static directory.

### B4. Voice-side destructive operations may select the wrong row

`navigate_to`, `delete_navpoint`, and `rename_navpoint` take `matches[0]` for a partial-name search. Duplicate or similar names can therefore navigate to, rename, or delete an unintended waypoint.

### B5. Retry and refit policies spend time without demonstrated recovery

The newest live run provides the first direct evidence for the pending retry decision. Ten refits recovered nothing and more than doubled attempt time. One five-attempt mark remained refused for 9.8 seconds.

### B6. Metadata, runtime text, and behavior disagree

Known examples:

- The prompt documents `list_navpoints(server_id, body)` while the tool accepts only `body`.
- `navigate_to` reports updates every five seconds regardless of the configured interval.
- The prompt describes arrival announcements and auto-stop generally, but the poll loop skips that logic for system-frame targets.
- The discovery description broadly promises distance and direction, while open-space direction is correctly withheld.

### B7. Token cost is high after activation

The skill exposes eight tools and carries a 6,684-character custom prompt, roughly 1,700 tokens before tool schemas. Progressive disclosure protects inactive conversations, but the prompt and schemas recur on every call after activation. `list_navpoints` also returns an unbounded list.

### B8. Release generation is not fail-safe

`update_release.py` removes the old release directory before validating every source. Missing files produce warnings and an incomplete release rather than stopping the build. The script also uses bare `print()` contrary to repository logging rules.
