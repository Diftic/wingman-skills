# NavPoint reader baseline, 2026-08-11

The first named baseline for `Supercalifragilistic.md` Wave 2 step 4. It measures
the **current** reader so a later optimisation has something honest to beat.

Produced by `ocr_dev/bench_reader.py`. Nothing in this file is a canonical
number: `ledger/LEDGER.md` owns those, and nothing here supersedes a row in it.

---

## READ THIS BEFORE QUOTING ANY MILLISECOND

**This is not a clean single-tenant baseline. The absolute milliseconds are an
upper bound.**

Three conditions applied and none of them is recoverable after the fact:

1. **Star Citizen was running when the run started and had exited before it
   finished.** The run sampled the game only at its two ends, so neither the
   moment it exited nor its CPU load before then can be recovered. An unknown
   early portion of these numbers was measured with the game up and the rest
   without it.
2. **Other agent processes were working on this machine throughout**, including
   a **competing `bench_reader.py --limit 12` run** started by the team lead at
   roughly the same time and killed part-way through.
3. **This run recorded no per-frame timestamps**, so **which frames overlapped
   the competing run cannot be determined**. It is not estimated here. The field
   was added to the tool afterwards; the next baseline can locate its own
   contamination, this one cannot.

**The ratios are more trustworthy than the absolutes.** Cold against warm
against self-heal, and fit against decode against parse, each had both sides
measured under the same contention. The wall-clock totals did not.

| machine | AMD Ryzen 7 7700X, 8 cores / 16 logical, 64 GB, Windows 11 build 26200 |
| python | 3.13.14, numpy 2.4.2 |
| reader | `overlay_glyphs.npz`, `POSITION_ROWS=8`, `REFUSE_COST=15.0`, `REFUSE_MARGIN=8.0` |
| corpus | **1028 frames over 23 sessions**, every frame on disk |
| wall clock | 768.7 s for the whole run |
| Star Citizen | running at the start, **exited during the run**, see the caveat above |

**What the harness runs** is exactly what `main.py:614-625` runs once the grab
returns: `capture_is_usable` then `overlay_is_present` then
`reader.read(POSITION_ROWS)` then `overlay_fields.capture_payload`, with one
`OverlayReader` per session so the alignment cache warms as it does in the field.

### What it cannot measure, and why

- **The raw screen-grab rate. Not measurable here at all.** Every frame came off
  disk and the tool never touches `mss`. Plan section 1 requires three rates kept
  apart; this harness can produce the second and third and **cannot** produce the
  first. No figure in this document may be quoted as a capture rate.
- **`scanner.parse_payload`.** The harness stops at `capture_payload`, the same
  boundary `stack_replay.py` draws and `LEDGER.md` records as boundary 1 of the
  corpus replay. "Accepted" here is one layer short of "the capture succeeded".
- **Availability over time.** These are stored frames. Decoding one twice is the
  same pixels twice, not two observations.
- **Star Citizen's CPU load**, for the reason in the caveat.

**No ledger figure was averaged into anything here.** The 831 ms live in-skill
median and the 4.5-to-4.9 s full-block figure are different paths on different
scenes; neither is combined with the other or with these numbers. This run is a
third thing again, decode-only from disk, and it replaces neither.

### The harness reproduces the ledger's independent availability figures

Three of today's four live sessions come out at exactly the rates
`CORPUS.md` and `LEDGER.md` recorded from a different tool and a different
parser: `jumppoint-pyro-nyx` 29/40 = 72 per cent, `pyro3-bloom-approach` 39/96 =
41 per cent, `pyro5-vuur` 78/156 = 50 per cent. `vuur-return-outside` was
recorded as "see below" and measures **146/200 = 73 per cent** here. That
agreement is the strongest evidence that this harness is reading the shipping
path correctly, and it is a check on the harness, not new evidence about the
reader.

### Brightness is not monotonic, and two sessions prove it

`surface-01` at bg 3.3 accepts everything, `pyro3-bloom-approach` at 61.3 accepts
41 per cent, `terrain-01` at 108.3 accepts nothing. That much matches the
ledger's bright limit.

**But `starfield` (bg 53.0) and `vote-fast` (bg 48.7) accept ZERO** while
`red-01` at bg 52.0 accepts 74 per cent. `starfield` is the Nyx glacier ring, a
**structured** background rather than a bright one. So a single background median
does not predict acceptance, and any future gate built on brightness alone would
be wrong about these two sessions. Structure and brightness are separate failure
causes and this run cannot separate them.

**`nosignal-01` is not a brightness data point at all.** It was captured with
`r_displayinfo 0`, so its 0 per cent is the overlay being switched off. It is in
the table because excluding a session because its result is inconvenient is worse.

### The main-menu phantom stacks inflate the corpus-wide rate

`login` and `login-black` accept **10 of 10** at bg 0.0. These are the main-menu
phantom stacks: a complete, markable capture produced with the player in no
container at all.

- corpus-wide accepted rate as measured: **647 of 1028 = 62.9 per cent**
- with the 10 main-menu frames removed: **637 of 1018 = 62.6 per cent**

**The decision has been made and is recorded.** `LEDGER.md` now carries
"**DECIDED by Lars 2026-08-11: REFUSE captures at the main menu**", which closes
what `Supercalifragilistic.md` section 3 left as an open product decision and
section 19 made a mandatory stop condition. **These 10 frames will therefore stop
being accepted**, so **62.6 per cent is the figure that survives the change** and
62.9 per cent is the one measured today.

The reader was not modified for this baseline, so the table above reports what
the shipping code did on 2026-08-11, not what it will do once the refusal lands.

reads**, because they were captured at 640 px. They are cheaper for that reason
and their timings are not comparable with the rest.

## 3. Cold against warm alignment, and the third case nobody costed

| alignment | n | p50 ms | p95 ms | max ms |
|---|---|---|---|---|
| **cold**, the fit ran inside the read | 38 | **901.2** | 1502.7 | 1731.6 |
| **warm**, cached origin | 724 | **468.1** | 700.2 | 1394.5 |
| **warm + self-heal** | 196 | **1266.1** | 1811.3 | 1915.7 |

**Cold minus warm at p50 is 433.2 ms, which is 48 per cent of a cold read.** The
alignment cache is worth roughly half of every read it serves.

Classification comes from the reader's own `last_from_cache` and `last_refit`,
not from a frame's position in its session. **Cold reads are not only the first
frame of a session**: `ALIGNMENT_REVALIDATE = 20` forces a refit every twenty
reads, which is why 23 sessions produced 38 cold reads.

### WARM + SELF-HEAL is the finding of this baseline

When a warm read decodes nothing trusted, `overlay_reader.read` assumes the
overlay may have moved, invalidates, refits and decodes **a second time**. That
path costs a fit plus two decodes: **1266 ms at p50, 2.70x a plain warm read**.

**It fired on 196 of 958 decoded frames, so roughly one read in five paid it.**
And it does not fire at random:

| `p5l2`, `game-mid`, `login`, `login-black` | 5 each | 1 | 4 | 0 | 0% | 100% |

**The share of self-heals runs broadly opposite to the acceptance rate.** Every
session that accepts everything pays it zero times, and the bright refusing
sessions pay it on half to four fifths of their reads. So **the frames least
likely to produce a fix are the most expensive to refuse**, and a scene gets
slower in proportion to how badly it is already failing. Availability and latency
are the same problem here, not two.

**One session breaks the pattern and the exception is instructive.**
`nosignal-01` accepts nothing yet self-heals on only 10 per cent of reads,
because it was captured with the overlay switched off. A blank row decodes as
spaces with zero refused cells, which makes it **trusted**, and the self-heal
only fires when nothing in the frame is trusted. So the trigger is "no row
decoded", not "no payload was produced", and a scene that is empty rather than
unreadable is cheap. Anyone reasoning about this path from the acceptance rate
alone would get that case wrong.

This is a description of measured behaviour and **not** a proposal to remove the
self-heal. It exists because a stale origin and an unreadable scene are
indistinguishable by cost alone, and the comment at `overlay_reader.py:719-728`
gives the reasoning. It is priced here so that whoever optimises the fast lane
knows what a refusing frame actually costs.

## 4. Where a cold read's time goes

Fit, decode and parse timed separately on 63 usable frames, three per session.
The fit through `fit_alignment`, the decode through `_decode_block` at the origin
that fit returned.

| part | n | p50 ms | p95 ms | max ms | share of the p50 sum |
|---|---|---|---|---|---|
| alignment fit | 63 | **384.4** | 925.6 | 1039.3 | **41.3%** |
| block decode | 63 | **546.5** | 705.7 | 742.1 | **58.7%** |
| semantic parse | 63 | **0.1** | 0.1 | 0.2 | 0.0% |

**The ledger's alignment-fit figure was a hypothesis and is now measured.**
`overlay_reader.py:87` carries "the fit is about 300 ms of a 870 ms read" as a
source comment. Measured here it is **384 ms**, higher than the guess. It is
**41.3 per cent of the summed parts** in the table above, and **42.7 per cent of
the cold `read` p50** in section 3, against the **34 per cent** the comment
implies. This did not come from re-averaging anything: it is a direct measurement
of `fit_alignment` on 63 frames.

**The semantic parse is free.** At 0.1 ms it is 0.0 per cent of the work, so
nothing in `overlay_fields` or `coordinate_stack` is worth optimising for speed.
All of the cost is pixels.

### Self-check, and the 454.7 ms gap in it

The split is only believable if it adds up to the whole thing measured through
the public API. On the 21 frames that appear in both passes, fit + decode has a
median of **919.9 ms** against a cold `read` median of **969.1 ms**, a 5 per cent
agreement. **The worst single-frame gap was 454.7 ms**, which is half a read and
deserves an explanation rather than a footnote.

The likeliest cause is the **alignment fit's own tail**. Its p50 is 384.4 ms and
its p95 is 925.6 ms, so the fit alone varies by more than 540 ms across this
corpus. The two measurements in a pair are taken at different moments, so a pair
where one caught a fit tail and the other did not produces exactly this size of
gap. Machine contention is the second candidate and cannot be separated from the
first in this run.

What it is **not**: the reader behaving differently between the two paths. Both
run the same fit and the same `_decode_block` in the same order, and the medians
agree to 5 per cent over 21 frames. A systematic split error would show as a
consistent offset, not as one outlier.

## 5. The three rates, kept apart

1. **Raw screen-grab rate: NOT MEASURABLE from stored frames.** Stated, not
   omitted.
2. **Decode-attempt rate: 958 of 1028 = 93.2 per cent.** The other 70 were
   rejected by the capture precondition before any decoding, which is the guard
   working as designed.
3. **Accepted authoritative-position rate: 647 of 1028 = 62.9 per cent**, or
   62.6 per cent with the main-menu frames removed. Per scene in section 1, which
   is the only form that means anything. One layer short of
   `scanner.parse_payload`, and a rate over stored frames rather than over time.

### What this says about the five-Hz gate

The cadence gate asks for five accepted fixes per second, which is a **200 ms**
budget per fix. The structural lane's **warm** p50 is **468 ms with no grab in
it**, so it is **2.3x over budget** before capture is added, and 6.3x over on a
self-healing frame. That is a measurement of why the plan has a fast lane, not an
argument against the target. Nothing here has been measured against the fast lane,
which does not exist yet.

## 6. The noise floor, and why it flatters this run

Five warm reads of one frame's identical pixels, `bright-01/frame_0002.png`:
p50 **458.3 ms**, min 457.7, max 460.0, **spread 0.5 per cent of p50**.

**Do not read that as this run's precision.** The noise measurement runs **last**,
after every session, by which point Star Citizen had exited and the competing
benchmark had been killed. It describes the quietest part of the run.

An earlier smoke run of the same check, on `p5l2` with four reads while the
machine was busy, measured a **7.4 per cent** spread. That figure is the weaker
measurement (fewer samples, and superseded by the 5-sample one under the tool's
final form), but it is the more honest guide to the contaminated window. **Treat
anything under 10 per cent as inside the noise of this baseline.**

## 7. How to take a clean baseline

This one is usable as an upper bound. A clean one needs all of:

1. **Single tenant.** No other agents, no test runs, and no second copy of this
   tool. That last one is not hypothetical: it happened to this run.
2. **Decide the game's state and hold it.** Star Citizen running under
   representative load is what plan section 10 asks for, and a game that exits
   mid-run gives neither state cleanly. The tool now samples the process between
   sessions, so an exit is bounded to one session instead of being invisible.
3. **The same command**, so two runs differ in the code and not the arguments.
   The command is printed in section 0 of every report and stored in the JSON.
4. **Compare against section 6 before believing an improvement.** Under
   contention the noise floor is the honest resolution of the whole report.

`python bench_reader.py --from-json <run>.json` re-renders a report from a saved
run. Use it rather than re-measuring to fix a table: re-measuring under different
load silently produces different numbers, which is the one thing a baseline must
not do.

## Defects found and fixed in the harness itself

Recorded because a benchmark that reports its own bugs is worth more than one
that does not.

- **Negative CPU.** The first render of this run printed "Star Citizen consumed
  -50554.4 s of CPU, which is -65.77 cores". The counter was fine: the game
  **exited during the run**, and the code subtracted a live baseline from a
  process that no longer existed. The probe now samples per PID, so an exit and a
  restart are both visible, and every branch that cannot support a number says so
  instead of printing one. The figure was re-derived from the saved JSON; the
  measurements were not repeated.
- **The wrong command named.** Re-rendering the saved run printed
  "(no arguments)" because that JSON predates the stored `argv`. A report that
  names a different command than the one that produced its numbers is worse than
  one that admits the gap, so a missing `argv` now prints as not recorded.
- **Locale hazard in the same probe.** The CPU value is now formatted with the
  invariant culture. On a machine whose locale writes decimals with a comma the
  previous form would have produced a string `float` rejects, and the probe would
  have reported itself as failed for a reason unrelated to the game.
- **Attribution pass built a fresh `OverlayReader` per frame.** The first decode
  against freshly allocated template arrays pays for a cold CPU cache, which put
  that pass about 20 per cent above the lane pass on the same frames and made the
  self-check look like a broken split. One reader per session, invalidated per
  frame, is both faster and the more faithful measurement.
